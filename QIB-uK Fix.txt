FIX-H2 — Scoping Capability Revocation to Its Own Slot

Status: Implemented, compiled, and test-validated (10/10 tests passing on Rust 1.75, cargo test).

The bug (FIX-H, v2)

CapabilityTable stamped every capability with a global CURRENT_EPOCH counter at mint time, and revoke() bumped that same global counter. lookup() rejected any capability whose stamped epoch was less than the current global epoch.

Since every other live capability was minted at some epoch strictly less than "current epoch + 1", a single revocation invalidated every other outstanding capability in the system on its next lookup — a self-inflicted, system-wide denial of service triggered by any legitimate revoke.

A minimal repro of the old logic confirms this directly:

// OLD (buggy) design — global epoch shared by every capability. fn revoke(&mut self, idx: usize) { self.caps[idx].alive = false; self.current_epoch.fetch_add(1, Ordering::SeqCst); // <-- the bug } A valid after revoking B? false C valid after revoking B? false 

Revoking capability B also silently killed unrelated capabilities A and C, which were never touched.

The fix (FIX-H2)

Replace the single global epoch with a generation counter per table slot. Revoking the capability in slot i bumps only slot i's generation; every other slot — and therefore every other capability — is completely unaffected.

Key changes:

Slot { cap: Option<Capability>, generation: u64 } replaces the bare Option<Capability> array. Each slot owns its own counter instead of reading a shared static CURRENT_EPOCH: AtomicU64.

Capability now stores slot_idx and generation (the slot's generation at mint time), not a system-wide epoch.

lookup() compares cap.generation != slot.generation — a mismatch only happens if that specific slot was revoked/reissued since the handle was minted.

revoke() bumps only slot.generation, never anything global.

require_attestation() is simplified: instead of the old epoch >= current_epoch.saturating_sub(1) grace-window hack (a workaround for the global-epoch design), it just checks for a live attestation capability. A revoked capability's slot is already None, so no epoch-comparison heuristic is needed at all.

Crate wiring needed to run the tests

Because qib-muk is #![no_std] at the crate root, the test harness (which needs std) requires one small change to main.rs:

// qib-muk/src/main.rs #![cfg_attr(not(test), no_std)] // was: #![no_std] #![no_main] 

heapless and spin both work identically under std and no_std, so this has no effect on the bare-metal build — it only allows cargo test to link against std for the test harness itself.

To independently confirm those regression tests are meaningful (i.e. that they would have failed against the old design), the old global-epoch logic was re-implemented in isolation and exercised directly:

// old (buggy) design, isolated for comparison only fn revoke(&mut self, idx: usize) { self.caps[idx].alive = false; self.current_epoch.fetch_add(1, Ordering::SeqCst); // <-- the bug } A valid after revoking B? false C valid after revoking B? false 

This confirms the old design does exactly what the review predicted — revoking B also invalidates A and C — and that the new slot-scoped design (validated above) eliminates that cross-contamination entirely.

What did not change

REVOCATION_PREEMPT_PENDING remains a global flag. This is intentional and out of scope for this patch: it's a coarse "re-check the currently running task" signal to the scheduler, not a capability-validity mechanism, and forcing a preemption check on any revocation is a reasonable conservative default. The bug fixed here was specifically that capability validity was being computed against a global counter, which is a correctness property, not a scheduling heuristic.

AttestationCap's temporal lease (valid_until_ns, FIX-G) is a separate, still-open gap (the lease isn't consulted by require_attestation) and is not addressed by this patch — it should be tracked as its own fix.
