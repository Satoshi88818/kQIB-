FIX-J — Making Scheduler::next_task() Actually Dequeue

Status: Implemented, compiled, and test-validated (27/27 tests passing on Rust 1.75, cargo test). Sits alongside the FIX-H2/FIX-G patches already applied to capability.rs in this same crate.

The bug

next_task() located the best candidate task by scanning ready_queue for the lowest (deadline, or deadline+priority) key, and returned a borrow into the queue — but never removed anything:

// OLD (buggy) next_task — selects, never removes pub fn next_task(&mut self) -> Option<&Task> { if self.ready_queue.is_empty() { return None; } if self.circuit_open { let idx = self.ready_queue.iter().enumerate() .min_by_key(|(_, t)| t.deadline_ns) .map(|(i, _)| i)?; Some(&self.ready_queue[idx]) } else { let idx = self.ready_queue.iter().enumerate() .min_by_key(|(_, t)| t.deadline_ns.saturating_add(t.priority as u64)) .map(|(i, _)| i)?; Some(&self.ready_queue[idx]) } } 

And tick() compounded it by discarding the result entirely:

if let Some(_task) = sched.next_task() { // Dispatch task — in a real kernel this would perform a context switch. } 

A minimal repro of the exact old logic confirms the consequence:

first call: Some(1) second call: Some(1) (BUG: should be None if it had dequeued) third call: Some(1) (BUG: same task forever) queue length after 3 calls: 1 (BUG: should be 0) 

Net effect: the same highest-priority task would be "selected" on every tick forever, ready_queue grew without bound as new tasks were submitted and nothing was ever removed, and current_task was never updated to reflect what had (nominally) run — which matters because FIX-H's revocation-preempt check (check_revocation_preempt) depends on current_task being accurate.

The fix

next_task() now removes the selected task and returns it by value. Selection still uses the same policy (pure EDF when circuit_open, deadline+priority otherwise), but once the index is chosen, self.ready_queue.swap_remove(idx) actually takes it out of the queue. swap_remove is fine here (no ordering to preserve) since the scheduling policy already picked the task by value, not by position.

next_task() sets current_task to the dispatched task's id as a side effect, so FIX-H's revocation-preempt bookkeeping reflects reality.

Selection logic is factored into select_index(), shared by next_task() (which mutates) and a new peek_next() (which doesn't) — so diagnostics/telemetry can look at what's next without perturbing scheduler state, and the two can never disagree about which task is next.

tick()'s dispatch site is now meaningful: next_task() already dequeues and updates current_task, so the body of the if let Some(task) block genuinely reflects "a task was dispatched," not a no-op placeholder.

This confirms the old code really does hand out the same task indefinitely and never drains the queue, and that the fixed next_task() (validated above) eliminates that entirely.

What did not change

Scheduling policy (pure EDF under circuit_open, deadline+priority otherwise) is byte-for-byte the same decision logic as before — this patch only changes what happens to the queue after the decision is made, not how the decision is made.

FIX-H's check_revocation_preempt logic is unchanged; it now simply has correct data (current_task) to act on, since next_task() finally sets it.

tick()'s three-step order (revocation check → drain P4 ring → schedule) is unchanged. Only the dispatch step's body changed from a discarded-result no-op to using the returned, already-dequeued Task.
