FIX-K — Reconciling Safe-Bypass with the TLA+ Liveness Property

Status: Implemented, compiled, and test-validated (34/34 tests passing on Rust 1.75, cargo test; the panic-handler/entry wiring itself compile-checked via cargo build). Sits alongside the FIX-H2/FIX-G/FIX-J patches already applied to this crate.

Design decision made explicit: main.rs's own doc comment says a fault hands routing off to "the P4/FPGA data plane" while the kernel is down — that framing only makes sense if the kernel is expected to come back. So this patch treats Safe-Bypass as recoverable, matching formal/MicrokernelScheduler.tla's existing SafeBypassEscapable property, rather than weakening the spec to assert a permanent halt. If that assumption is wrong for this system, the correct move is the opposite one (delete SafeBypassEscapable from the spec) — flagging that fork here since it's a genuine design choice, not something derivable from the code alone.

The mismatch

main.rs's panic handler set SAFE_BYPASS_ACTIVE and spun forever:

// OLD panic handler — sets the flag, then can never clear it #[panic_handler] fn panic_handler(_info: &core::panic::PanicInfo) -> ! { SAFE_BYPASS_ACTIVE.store(true, Ordering::SeqCst); loop { core::hint::spin_loop(); } } 

formal/MicrokernelScheduler.tla asserts:

SafeBypassEscapable == safe_bypass => <>(\neg safe_bypass) 

i.e. the system is required to eventually leave Safe-Bypass. An infinite spin loop can never satisfy that — and this isn't just an intuition. The compiler itself proves it: panic_handler's signature returns ! ("never"), and Rust's own unreachable-code analysis confirms nothing can follow a call to a -> ! function:

--> old_safe_bypass_check.rs:26:5 | 22 | old_panic_handler(); | ------------------- any code following this expression is unreachable ... 26 | println!(...); | ^^^^^^^^^^^^^ unreachable statement 

So "eventually leaves Safe-Bypass" cannot mean "the same execution context climbs back out of the spin loop" — the type system rules that out structurally, not just as a matter of the loop happening to never break. It has to mean something outside that execution context resets the node.

The fix: a watchdog timer

A hardware watchdog timer (WDT) is the standard bare-metal mechanism for exactly this. Normal kernel operation periodically "pets" (kicks) the watchdog to prove it's alive; if the watchdog goes WATCHDOG_TIMEOUT_NS without being pet, it forces an unconditional reset of the whole chip, and _start runs again from fresh, zero-initialized state — SAFE_BYPASS_ACTIVE included. Because the panic handler's spin loop never calls pet() again, entering Safe-Bypass guarantees the watchdog fires and the node resets.

Two pieces:

watchdog.rs — the testable policy: pet-tracking, expiry logic, and a ResetSink trait that abstracts the one genuinely untestable operation (forcing a real hardware reset) behind a seam a test can observe safely.

entry.rs — the actual kernel wiring: _start() pets the watchdog every loop iteration; the panic handler deliberately never does. Compiled only outside test builds, for the same reason the crate is only no_std outside test builds — a custom #[panic_handler] would collide with std's own panic runtime under cargo test.

A /// test implementation records that a reset was requested instead, so /// tests can assert *that* a reset would have fired without tearing down /// the test process — you cannot meaningfully unit-test "the chip reboots" /// on a hosted test runner, so this seam is where that limit is drawn /// explicitly rather than papered over. pub trait ResetSink { /// On real hardware this never returns. Test implementations may /// return so the harness stays alive to make assertions. fn trigger_reset(&self); } /// The watchdog's *policy*: whether it currently considers itself expired, /// given its pet history. Deliberately independent of `ResetSink` — this is /// the part FIX-K's correctness argument rests on, and the part validated /// by the unit tests below. pub struct Watchdog { last_pet_ns: AtomicU64, armed: AtomicBool, } impl Watchdog { pub const fn new() -> Self { Self { last_pet_ns: AtomicU64::new(0), armed: AtomicBool::new(false) } } /// Arm the watchdog (if not already armed) and reset its countdown from /// `now_ns`. This is what the main loop calls every tick to prove /// liveness, and what the panic handler must — and does — never call /// again once it starts spinning. pub fn pet(&self, now_ns: u64) { self.last_pet_ns.store(now_ns, Ordering::SeqCst); self.armed.store(true, Ordering::SeqCst); } pub fn is_armed(&self) -> bool { self.armed.load(Ordering::SeqCst) } /// `true` if, as of `now_ns`, more than `WATCHDOG_TIMEOUT_NS` has /// elapsed since the last `pet()`. An unarmed watchdog never expires — /// this mirrors real WDT hardware, which must be explicitly armed /// before it can fire, and keeps "never booted/never armed" distinct /// from "armed and starved." pub fn is_expired(&self, now_ns: u64) -> bool { if !self.armed.load(Ordering::SeqCst) { return false; } let last = self.last_pet_ns.load(Ordering::SeqCst); now_ns.saturating_sub(last) >= WATCHDOG_TIMEOUT_NS } /// Check-and-act: if expired as of `now_ns`, invoke `sink` and report /// `true`. Called from the main loop's own tick as a software-level /// backstop alongside real WDT hardware (defense in depth), and is also /// the mechanism exercised directly by the tests below to model what /// happens once the panic handler stops petting. pub fn check_and_maybe_reset(&self, now_ns: u64, sink: &dyn ResetSink) -> bool { if self.is_expired(now_ns) { sink.trigger_reset(); true } else { false } } } /// Global, shared watchdog instance. `_start()` pets this every tick; /// `entry.rs`'s panic handler deliberately never does. pub static WATCHDOG: Watchdog = Watchdog::new(); Boot. wd.pet(now); // 2. Normal operation for a while: tick + pet, same as production. for _ in 0..20 { now += crate::consts::ISOCHRONOUS_TICK_NS; wd.pet(now); assert!(!wd.check_and_maybe_reset(now, &sink)); } assert_eq!(sink.count(), 0, "no reset during normal, healthy operation"); let last_healthy_pet = now; // 3. qib-muk/src/entry.rs (new file — replaces the panic handler / _start in main.rs):

//! Stand-in for the panic-handler / `_start` portions of `qib-muk/src/main.rs`. //! //! FIX-K's actual behavioral change lives here: the panic handler must //! *never* call `WATCHDOG.pet()`, and the main loop must call it every //! tick. This module is compiled only under `#[cfg(not(test))]` because a //! `#[panic_handler]` would collide with `std`'s own panic runtime under //! `cargo test` — the exact same reason `#![no_std]` itself is only applied //! under `#[cfg(not(test))]` at the crate root. It is exercised by //! `cargo build` (typechecked as part of the normal, non-test build) rather //! than by a unit test, since "does the physical chip actually reset" is //! not something a hosted test process can observe — see `watchdog.rs` for //! the policy-level tests that validate the logic this wiring depends on. use crate::watchdog::WATCHDOG; use core::sync::atomic::{AtomicBool, Ordering}; /// Global Safe-Bypass flag. When `true` the kernel has faulted and routing /// is delegated to the P4/FPGA data plane. pub static SAFE_BYPASS_ACTIVE: AtomicBool = AtomicBool::new(false); #[panic_handler] fn panic_handler(_info: &core::panic::PanicInfo) -> ! { SAFE_BYPASS_ACTIVE.store(true, Ordering::SeqCst); #[cfg(feature = "baremetal-arm")] crate::hw::uart::write_str( "[QIB-\u{3bc}K] PANIC \u{2014} Safe-Bypass engaged; watchdog will reset the node\n", ); // FIX-K: deliberately do NOT call WATCHDOG.pet() here, ever. Safe-Bypass's // liveness guarantee (formal/MicrokernelScheduler.tla's // SafeBypassEscapable) depends entirely on the watchdog going un-pet // from this point on and forcing a hardware reset — see watchdog.rs for // the full argument. Petting it here to "be safe" would silently // recreate the exact bug this patch fixes. loop { core::hint::spin_loop(); } } #[no_mangle] pub extern "C" fn _start() -> ! { crate::hw::timer_init(); crate::capability::init(); crate::scheduler::init(); // FIX-K: arm the watchdog at boot. On a real reset, this is the first // proof-of-life the hardware WDT sees. WATCHDOG.pet(crate::hw::now_ns()); loop { crate::scheduler::tick(); crate::hw::p4::dispatch_pending_stub(); // FIX-K: pet every tick. This is the line whose absence during a // panic is what makes the reset happen — its presence here is what // keeps a healthy node from ever resetting. WATCHDOG.pet(crate::hw::now_ns()); } }

All 27 pre-existing tests (FIX-H2, FIX-G, FIX-J — untouched by this patch) plus 7 new watchdog tests, most importantly:

panic_then_missed_pets_deterministically_triggers_reset — the direct regression test for FIX-K. It simulates the exact real sequence: boot → 20 ticks of healthy pet-every-tick operation (no reset) → a panic that stops petting → 49 more ticks of silence (still no reset — proving it doesn't fire early) → one more tick crosses WATCHDOG_TIMEOUT_NS and the reset sink fires exactly once. This is the strongest test of the liveness property available on a hosted runner: it can't literally reboot a chip, but it proves the precise condition ("stopped petting because we're stuck in the panic spin loop") deterministically leads to "reset triggered" within bounded time.

repeated_pets_prevent_expiry_indefinitely — 10,000 simulated ticks of normal, healthy operation never trip the watchdog — confirms the fix doesn't introduce spurious resets.

expires_once_timeout_elapses_without_a_pet — boundary check: one nanosecond under the timeout is not expired, exactly at it is.

unarmed_watchdog_never_expires / check_and_maybe_reset_is_a_no_op_while_unarmed — an un-pet, never-armed watchdog (e.g. before _start() runs its first loop iteration) can't spuriously fire.

Confirming the old design really had no escape

To make sure this patch is fixing something real and not a spec artifact, the old design (no watchdog, just the spin loop) was checked directly. The Rust compiler's own unreachable-code lint on a diverging panic handler is structural proof that nothing downstream of it can execute — there simply is no code path, anywhere in the old design, that could ever clear SAFE_BYPASS_ACTIVE. That's not a bug that manifests probabilistically; it is true by construction of the type signature.

What this patch does not attempt

It does not (and cannot) unit-test an actual hardware reset. The ResetSink trait exists specifically to draw that line honestly: real hardware writes a WDT control register and never returns; the test implementation records the request so assertions can be made without tearing down the test process. Treat cargo test as validating "the watchdog's policy is correct" and cargo build as validating "the wiring typechecks," not as proof the physical reset happens — that last step is inherently outside what a hosted test can observe.

The TLA+ spec was not mechanically re-checked. formal/MicrokernelScheduler.tla as written already states SafeBypassEscapable; this patch makes the Rust implementation actually satisfy it (a watchdog-forced reset is exactly the kind of external event <> quantifies over), but re-running TLC against the spec requires the TLA+ toolchain, which isn't available in this environment (no network path to it from this sandbox). If a fully rigorous closure of this item matters, the spec should additionally gain an explicit WatchdogReset action (safe_bypass /\ safe_bypass' = FALSE) with a weak-fairness assumption, and be re-checked with TLC — flagging this as the one piece of "validated" that means "compiled and tested in Rust" rather than "model-checked," to be transparent about the boundary.

WATCHDOG_TIMEOUT_NS (50 ticks) is a starting default, not a tuned value — the real number should be chosen based on the actual worst-case jitter of the isochronous tick and how quickly the P4/FPGA fallback needs the kernel back, which is a systems-engineering question this patch doesn't have the data to answer.
